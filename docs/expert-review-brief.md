# 离线情报分析工作台项目审核说明

本文用于给外部专家快速了解项目上下文、当前问题、后续设计取舍与审核重点。专家不需要查看代码库，也能据此判断该课程作业方向是否合理、是否契合最新要求、后续应如何收束。

## 一、课程背景与最新要求

本项目是“大模型编程实践”类课程作业。课程过程中，老师曾多次调整要求与评分侧重点。根据目前最新口径，作业不再要求固定功能清单，而是更重视以下几项：

1. **契合实际场景**：项目应服务一个真实、明确的业务场景，而不是泛泛展示 AI 能力。
2. **有创新性和亮点**：不能只是调用大模型或套一个聊天壳子，需要体现自己的业务逻辑、算法设计或系统约束。
3. **工作量充分**：需要体现完整系统工程，而不是单点 demo。
4. **有逻辑和可解释性**：功能之间要形成闭环，用户流程要清楚。
5. **界面用户友好**：面向实际用户，尤其是非技术用户，不能让用户直接面对模型、prompt、token 等技术细节。
6. **需要完整的数据管理和权限管理**：系统不只是一个 AI 分析页面，还应有数据组织、用户角色、权限控制、审计等管理能力。

最终交付物包括：

- 代码仓库；
- 现场演示；
- 实验报告。报告按正常技术总结报告组织，包含研究背景与意义、主要功能与总体架构、主要模块与技术实现、创新点、工作情况总结等。

## 二、项目当前定位

项目当前名称可概括为：

**离线情报分析工作台：面向受控 / 涉密 / 气隙环境的多源情报线索核验系统。**

核心业务场景是：情报分析人员拿到一批异构材料，例如简报、通话转写、日志、图片、视频帧、扫描件等，需要在本地受控环境中完成素材管理、线索提取、交叉核验、矛盾发现、问答追查、报告生成与审计留痕。

这个定位比“聊天机器人”更合适，因为情报场景的关键不是自由对话，而是：

- 材料是否被妥善管理；
- 结论是否能回到原始证据；
- 不同来源之间是否存在冲突；
- 谁在什么时候做了什么操作；
- 用户是否只能看到自己权限范围内的数据；
- 报告是否经过人工复核才能导出。

## 三、项目现有基础

当前项目已经不是空壳，已有较多工程基础。整体是 TypeScript monorepo，分为三个包：

- `packages/core`：自研 agent runtime / CLI / tool / skill 基础设施；
- `packages/server`：Express 后端，包含专题、素材、问答、要素、矛盾检测、报告、审计、鉴权等服务；
- `packages/web`：React + Vite 前端，包含作业面、管理面和审计面。

当前已经实现或部分实现的能力包括：

1. **专题管理**
   - 创建专题；
   - 按密级过滤专题；
   - 专题内管理素材、问答、要素、矛盾、报告、审计。

2. **素材管理**
   - 支持文档、音频、视频、图片等素材类型；
   - 文档切块；
   - 媒体素材加工入口；
   - 素材状态、删除、重建索引。

3. **带溯源问答**
   - 问答结果绑定引用；
   - 引用指向素材片段；
   - 使用内容 hash 校验，降低伪造引用风险。

4. **要素抽取**
   - 从已加工材料中抽取人物、组织、地点、事件、装备、时间等要素；
   - 要素提及绑定原始素材出处。

5. **矛盾检测**
   - 从材料中抽取主张；
   - 对同一实体相关陈述做聚类和成对判断；
   - 输出跨文件或文件内矛盾；
   - 每条矛盾两侧都绑定出处。

6. **关系网络与时间线**
   - 基于要素共现生成关系网络；
   - 基于时间类要素生成时间线；
   - 这部分尽量采用确定性聚合，而不是让大模型直接编造图谱。

7. **报告与复核**
   - 报告草稿、提交复核、核准、导出；
   - 导出前有状态闸门；
   - 部分事实内容要求有引用支撑。

8. **权限与审计**
   - 用户登录；
   - 角色包括作业员、管理员、保密员；
   - 密级包括内部、秘密、机密、绝密；
   - 审计日志采用哈希链思路；
   - 关键操作入审计。

9. **离线 / 零外发设计**
   - 模型调用通过统一出站授权控制；
   - 生产部署目标是本地模型或内网模型；
   - 云模型只作为开发期替身。

## 四、当前主要问题

虽然已有工作量不少，但当前完成效果不理想，主要问题不是“没有功能”，而是**功能过度铺开、主线不清、演示弱、UI 信息密度和层级控制不足**。

### 1. 功能过度设计，演示主线被淹没

当前系统包含 runtime、模型槽、RAG、素材、多模态、问答、要素、矛盾、报告、审计、管理后台等很多模块。代码层面工作量很大，但现场演示时容易变成“到处点功能”，而不是让老师清楚看到一个完整业务闭环。

课程作业更需要的是一个强叙事：

> 多源材料进入系统，系统帮助情报人员发现关键要素和冲突说法，并把每个结论绑定到原始证据，最终形成可复核、可审计的报告。

### 2. UI 缺少“情报工作台”的一屏价值感

当前 UI 偏工程后台，功能入口较多，但核心分析价值没有集中呈现。用户进入专题后，应该马上看到：

- 有多少素材；
- 加工状态如何；
- 抽取了哪些关键对象；
- 发现了哪些矛盾；
- 哪些矛盾风险最高；
- 每条结论能否点回证据；
- 报告流程进行到哪一步。

当前这些信息分散在多个 tab 中，演示时不够直接。

### 3. 数据管理和权限管理需要被显式讲清楚

老师强调完整的数据管理和权限管理，因此不能只讲 AI 分析。需要把以下能力作为系统完整性的一部分展示出来：

- 专题数据生命周期；
- 素材上传、加工、删除、重建索引；
- 分析产物管理；
- 用户角色；
- 密级裁剪；
- 审计日志；
- 报告复核权限。

### 4. 报告叙事可能过满

现有报告倾向于把所有技术点都写进去，容易显得“堆概念”。更好的写法是围绕核心业务闭环展开：

- 为什么情报场景需要本地、可溯源、可审计；
- 系统如何管理数据和权限；
- AI 在哪里参与；
- 哪些环节是我们自研的确定性逻辑；
- 如何证明不是简单套壳。

### 5. 工程基线原先存在包管理混乱

项目实际应使用 pnpm，但此前仓库存在 npm workspace 脚本和 `package-lock.json`，缺少 `pnpm-workspace.yaml`。这会影响复现、验收和专家审阅。当前已初步修正为 pnpm workspace，并补充了 pnpm lock。

## 五、我的总体设计思路

我的建议是：**不继续加大功能面，而是把系统收束成“双主线”产品。**

### 主线 A：情报作业主线

面向作业员，强调实际研判流程：

1. 新建专题；
2. 上传多源素材；
3. 查看素材加工状态；
4. 抽取要素；
5. 查看关系网络和时间线；
6. 检测跨材料矛盾；
7. 对矛盾和问答结论点开出处复核；
8. 形成研判结论；
9. 生成并提交报告。

### 主线 B：管理治理主线

面向管理员和保密员，强调完整系统管理能力：

1. 用户管理；
2. 角色和密级权限；
3. 专题与素材数据管理；
4. 模型 / 能力状态查看；
5. 审计日志查询；
6. 审计链校验；
7. 报告复核和导出控制。

这两个主线共同回答老师关注的问题：

- 是否有真实业务场景：有，情报材料核验与报告；
- 是否有完整系统：有，数据、权限、审计、报告闭环；
- 是否有创新点：有，结构化矛盾检测和可验证溯源；
- 是否不是套壳：不是，LLM 只是组件，系统有明确业务规则和约束；
- 是否用户友好：通过 UI 收束，让非技术用户按专题流程操作。

## 六、建议保留的核心亮点

### 1. 可验证溯源

这是情报场景的根基。系统不能只给出“看似合理”的 AI 答案，而要让每条事实性结论回到材料片段。

设计重点：

- 素材被切成 chunk；
- 每个 chunk 计算 `content_hash`；
- 引用必须指向真实 chunk；
- 模型生成的引用若无法匹配真实材料，则丢弃或标记为待核；
- UI 中引用可以点击查看原文、时间码、图片区域或视频帧。

专家审核重点：

- 这种机制是否足以支撑“可复核”的课程亮点；
- 报告中如何准确描述，避免过度声称“完全防止幻觉”。

### 2. 结构化矛盾检测

这是最重要的创新点。不要把它讲成“大模型帮我找矛盾”，而要讲成：

> 系统先把材料拆成可追踪主张，再按实体聚类，只在相关主张之间进行成对判断，最后输出带出处的矛盾线索。

可强调的差异：

- 直接让 LLM 找矛盾：黑盒、不可控、难以覆盖大语料、出处不稳；
- 本项目做法：逐块抽取、局部判断、每条矛盾绑定证据、可分批覆盖、可审计。

专家审核重点：

- 该设计是否足以构成课程意义上的“非套壳”；
- benchmark 应如何呈现，避免夸大。

### 3. 数据与权限治理

老师已强调完整的数据管理和权限管理，所以必须作为亮点之一。

建议突出：

- 专题是数据组织单位；
- 素材、要素、矛盾、问答、报告都是专题内产物；
- 用户按角色和密级访问；
- 低权限用户看不到高密级专题；
- 保密员负责复核；
- 管理员负责用户和能力配置；
- 关键操作进入审计日志。

专家审核重点：

- 管理能力是否满足“完整系统”要求；
- 是否需要进一步补齐角色权限矩阵。

### 4. 离线 / 气隙友好

该点适合放在背景意义和系统约束中，不宜作为唯一创新点。

强调方式：

- 情报材料敏感，不能默认上传云端；
- 系统设计允许替换为本地模型；
- 出站调用需要授权；
- 审计外发行为。

专家审核重点：

- 对课程来说，“离线可部署”是否加分；
- 是否需要弱化涉密表述，避免过度军事化或不必要敏感。

## 七、建议弱化或隐藏的内容

为了让项目更像一个完成度高的课程作品，而不是未收束的大工程，建议演示和报告中弱化以下内容：

1. **mini-agent runtime 细节**
   - 它是底层基础设施，不是老师最关心的业务亮点。

2. **复杂模型槽配置**
   - 可以说“模型可替换”，但不现场展开每个 provider 和 env。

3. **多 agent 编排**
   - 如果没有强展示效果，不作为主线。

4. **过多 RAG 变体**
   - Contextual Retrieval、HyDE、query rewrite 等可以放实验附录，不应喧宾夺主。

5. **过多管理后台配置项**
   - 管理后台要展示用户、权限、审计、模型状态即可，不要让专家觉得系统重点跑偏到配置平台。

## 八、建议的界面重构方向

### 1. 首页：数据管理入口

首页应体现“完整数据管理”，而不是简单卡片列表。

建议包含：

- 专题列表；
- 搜索；
- 新建专题；
- 密级标签；
- 素材数量；
- 分析状态；
- 最近更新时间；
- 快速进入工作台。

如果时间允许，可以把卡片改为更适合管理系统的表格 / 列表，便于展示数据管理能力。

### 2. 专题工作台：一屏看到核心研判状态

专题页顶部应有“研判概览”：

- 素材总数 / 已加工数；
- 抽取要素数；
- 发现矛盾数；
- 高风险未处理矛盾数；
- 报告状态；
- 审计状态。

主体建议按三栏组织：

- 左侧：素材与状态；
- 中间：要素、时间线、矛盾；
- 右侧：证据详情、问答、报告动作。

如果不大改代码，也可以保留 tab，但在视觉上强化“矛盾检测”和“溯源复核”为中心。

### 3. 矛盾检测页：作为主演示页面

该页面应重点打磨：

- 每条矛盾显示“陈述 A / 陈述 B”；
- 显示来源材料；
- 显示置信度和跨文件 / 文件内；
- 显示处理状态：未处理、已解决、已忽略；
- 点击引用能看到原文；
- 保密员 / 管理员可以处理矛盾。

这页最能体现创新性和业务价值。

### 4. 权限管理页：必须可演示

用户管理页需要清楚展示：

- 用户名；
- 角色；
- 密级；
- 是否启用；
- 创建 / 修改 / 禁用 / 重置口令等能力。

如果当前功能不完整，至少应把“角色 + 密级裁剪 + 后端强制”演示清楚。

### 5. 审计中心：证明系统完整性

审计页建议展示：

- 操作时间；
- 用户；
- 动作；
- 对象；
- 结果；
- 哈希链校验状态；
- 拒绝 / 失败操作。

演示时应刻意展示一次越权或导出被拒绝，再在审计中看到记录。

## 九、建议的现场演示流程

建议控制在 5 到 8 分钟，避免到处点。

### 演示前准备

准备一个固定演示专题，例如：

**“港口异常活动线索核验”**

包含 6 到 8 份材料：

- 港口值班日志；
- 船舶活动简报；
- 一段通话转写；
- 一张带 OCR 信息的图片；
- 一段视频帧描述；
- 一份来源不同但说法冲突的报告。

材料中应故意植入 2 到 3 处矛盾，例如：

- 同一船只出现时间不一致；
- 货物数量不一致；
- 是否进入某区域说法不一致；
- 某人员是否在场说法不一致。

### 演示步骤

1. **作业员登录**
   - 展示只能看到权限范围内专题。

2. **进入专题**
   - 展示素材列表、加工状态、密级。

3. **数据管理**
   - 上传一份材料；
   - 展示状态变化；
   - 展示可删除 / 重建索引 / 重新加工。

4. **要素与时间线**
   - 点击提取要素；
   - 展示人物、组织、地点、事件、时间；
   - 展示关系网络或时间线。

5. **矛盾检测**
   - 点击检测；
   - 展示跨文件矛盾；
   - 点击陈述 A / B 的引用，回到原始证据。

6. **问答追问**
   - 提问：“哪些线索说明该船只的到港时间存在冲突？”
   - 展示回答带引用。

7. **保密员复核**
   - 切换保密员账号；
   - 处理一个高风险矛盾；
   - 提交并核准报告。

8. **管理员 / 审计**
   - 切换管理员；
   - 展示用户角色和密级；
   - 展示审计中心；
   - 展示哈希链校验。

### 演示结束语

建议总结为：

> 本系统不是简单聊天机器人，而是一个围绕专题数据管理、权限控制、证据溯源和交叉核验构建的情报工作台。大模型只承担抽取和判断中的部分任务，关键的引用校验、权限裁剪、审计、报告闸门和矛盾组织逻辑由系统结构保证。

## 十、实验报告建议结构

报告不宜写成开发流水账，也不宜堆过多名词。建议如下：

### 1. 研究背景与意义

说明多源情报材料处理的痛点：

- 材料来源多、格式杂；
- 人工阅读和交叉比对耗时；
- 大模型直接总结容易缺少出处；
- 敏感材料不能随意外发；
- 报告需要复核和审计。

### 2. 系统需求分析

分为业务需求和非功能需求：

业务需求：

- 专题化管理；
- 素材管理；
- 要素抽取；
- 矛盾检测；
- 溯源问答；
- 报告生成；
- 审计。

非功能需求：

- 权限控制；
- 密级裁剪；
- 离线部署；
- 可复核；
- 可审计；
- 失败可见。

### 3. 总体架构

说明三层架构：

- 前端工作台；
- 后端业务服务；
- agent / 模型适配基础设施；
- 文件式本地数据存储。

重点讲数据流：

`素材上传 → 加工切块 → 建索引 → 要素 / 主张抽取 → 矛盾检测 → 问答引用 → 报告复核 → 审计`

### 4. 主要模块与技术实现

建议分模块：

- 数据管理模块；
- 权限管理模块；
- 素材加工模块；
- 检索与问答模块；
- 矛盾检测模块；
- 报告与审计模块。

### 5. 创新点

建议写 3 个，不要写太多：

1. 面向情报核验的结构化矛盾检测；
2. 基于内容 hash 的可验证引用溯源；
3. 数据、权限、审计一体化的离线工作台设计。

### 6. 实验与效果分析

可以包含：

- 检索 benchmark；
- 矛盾检测 benchmark；
- 与大模型直出的对比；
- 负结果说明。

注意：如果当前矛盾检测 F1 只是追平直出，不要写“显著优于”。应写：

> 在小规模标注语料上，结构化方案与大模型直出 F1 持平，但额外提供逐条出处、全语料分批覆盖、审计和可复核能力。

这更诚实，也更有工程说服力。

### 7. 工作总结与不足

如实写不足：

- UI 仍可进一步简化；
- 多模态模型依赖本地服务部署；
- 矛盾检测对实体归一化仍有改进空间；
- 演示语料规模有限；
- 报告导出格式可继续完善。

## 十二、希望专家重点审核的问题

请专家重点判断以下问题：

1. 以“离线情报分析工作台”作为课程作业主题是否合适？
2. 当前主线“多源材料管理 + 权限治理 + 矛盾检测 + 溯源报告”是否契合老师最新要求？
3. 结构化矛盾检测是否足以构成创新点，而不是简单套壳？
4. 数据管理和权限管理展示到什么程度才算“完整”？
5. 演示是否应突出“矛盾检测”，还是应更突出“完整管理系统”？
6. 报告中关于离线 / 涉密 / 情报场景的表述是否需要收敛，避免过度敏感或夸大？
7. benchmark 当前“追平大模型直出但增加可溯源和审计”的表述是否有说服力？
8. 是否建议砍掉某些现有功能，避免专家认为项目过度设计？

## 十三、当前结论

我的判断是：

1. 项目方向本身是可取的，且符合最新要求中的真实场景、工作量、创新性、数据管理和权限管理。
2. 当前主要风险不是功能不足，而是功能过散、UI 主线不强、报告叙事过满。
3. 后续最重要的不是继续添加新能力，而是围绕一个强业务闭环做收束。
4. 最适合答辩的表达是：

   **这是一个面向多源情报材料核验的离线工作台，核心价值是把数据管理、权限控制、证据溯源、矛盾检测和报告复核串成完整闭环。**

5. 最应突出的创新点是：

   **结构化矛盾检测 + 可验证溯源 + 权限审计闭环。**

6. 最应避免的表达是：

   - “我们做了一个通用 Agent 平台”；
   - “我们接了很多模型”；
   - “大模型自动完成情报分析”；
   - “完全解决幻觉问题”；
   - “所有功能都很完整”。

更稳妥的表达是：

> 系统将大模型能力嵌入情报分析流程，但关键结论必须绑定证据，关键操作必须受权限和审计约束。相比直接让大模型生成答案，本系统更强调可复核、可追踪和可治理。
